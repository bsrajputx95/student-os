**StudentOS: completion audit and proposed V1 scope**

Audited 20 October 2026. Scope: the active application in `B:/STUDENTOS/studentos-web`, compared with the student, teacher, placement, social, assessment, and journey requirements in this conversation.

This is an implementation audit, not a penetration test, a load test, or an accessibility certification. Findings below come from source inspection, catalog counts, the existing test suite, and isolated in-memory reproductions. No real campus records were edited. No features were implemented during this audit.

**1. Current position**

StudentOS has a connected local application with substantial working workflows. It is suitable for exploring the product and testing a sample campus. It still needs stronger content, verified learning evidence, several flagship features, institution administration, and deployment operations before a real college pilot.

There is no useful single completion percentage: a working navigation item can contain a complete local workflow, a partially implemented service, or a content scaffold. Those have different remaining costs.

| Area | Current evidence | Meaning |
| --- | --- | --- |
| Student and staff accounts | Password login, student registration, hashed passwords, cookie sessions, teacher/placement checks | Working local identity; institutional enrollment, account recovery, provisioning, and full session lifecycle are incomplete |
| Sample campus | 400 seeded students, 100 per year; 100 staff | Populated demonstration, with fictional people and history explicitly labelled |
| Practice catalog | 3,300 entries: 3,294 external LeetCode links and six browser JavaScript exercises | A large discovery library; most problems are solved on LeetCode and recorded manually |
| Assessment lab | Five debugging projects and six SQL exercises | Starter ZIPs, drafts, timed attempts, checks, explanations, and saved results work; project results are browser practice |
| Quizzes | 10 sets, 44 questions in total | 32 new core-CS/aptitude questions plus 12 older questions; a small fixed bank |
| Learning | Six courses with 122 lesson labels; one embedded video course | Labels and progress exist, but most lessons do not have individually authored instructional content |
| Projects | Four templates with checkable milestones | Connected to progress and resume; project evidence is self-reported |
| Opportunities | 35 sourced snapshots; 20 company guides; four early-career program links | Useful curated starting material; no continuous refresh or automatic closing detection |
| Events | Three external catalog entries, all associated with Hacktoberfest; 104 seeded college events | External breadth is narrow; college history is illustrative |
| Journey | Long scrollable map, eight phases, 150-day final-year default, other year defaults, custom deadlines, rest and leave | Calendar scheduling works; mastery-driven planning and enough curriculum depth remain incomplete |
| College workflows | Audience targeting, publication, submissions, grading, revisions, guidance, cohorts, CSV, placement drives | Connected local flows; administration and several real academic/placement operations remain incomplete |
| Social | Shared student/staff feed, year badges, follows, comments, college updates, global chat and participant-only DMs | Core sharing works; moderation, privacy controls, and richer messaging are absent |
| Regression checks | All 46 current model/HTTP tests passed during this audit | Good baseline; the reproduced issues below are outside the present assertions |

**2. Confirmed logic gaps to fix first**

Priority here means release order, not a formal security severity. P0 = fix before a real college pilot or relying on rankings; P1 = required to finish the core V1 promise; P2 = useful after the core pilot works.

| ID | Priority | Finding and evidence | Required outcome |
| --- | --- | --- | --- |
| B01 | P0 | `task.complete` marks coding/course/project tasks complete and awards XP/skill without completing their resource. Reproduction: a React lesson task became complete, Frontend increased to 1 and XP to 30, while React course progress stayed at zero. `server/model.mjs:83`; checkbox in `src/components/ui.jsx:27`. | Checkboxes open evidence-producing work. Completion derives from the linked lesson, attempt, exact milestone, or an explicitly labelled self-report. A single activity cannot earn duplicate awards through task and resource paths. |
| B02 | P0 | Repeating one perfect quiz ten times awarded 500 XP and 20 Frontend points, independent of new learning. `server/model.mjs:104`. | Keep attempt history, but cap/restrict repeated rewards. Separate practice activity from mastery improvement and verified assessment evidence. |
| B03 | P0 | Overview/Journey task shortcuts ignore a quiz task's `resourceId`. An isolated call assigned `os-fundamentals` but opened `sql-check`, because category selects a generic quiz. `src/components/ui.jsx:28`. The DayMission dialog uses the correct ID, so different entry points disagree. | All entry points open the exact same resource and its successful completion satisfies that task. |
| B04 | P0 | One quiz attempt grades every assignment with that quiz template ID. Reproduction: one attempt graded two distinct assignments; a later zero-score practice attempt reset both grades to zero. `server/model.mjs:135`. | Submit using a particular assignment and attempt ID. Define permitted retakes and grade policy; freeze historical reviews and respect closing rules. |
| B05 | P0 | Replaying an already completed project milestone can complete today's new project task for the same project. Reproduction: milestone zero remained the only completed milestone, but the new task became complete. Matching uses project ID, not exact milestone. `server/model.mjs:107,130`; missions currently lack a milestone identifier. | Store and match an exact milestone/version/evidence ID. Replays cannot satisfy different work. |
| B06 | P0 | Invalid profile scheduling types pass validation. Reproduction accepted `dailyMinutes: 'not-a-number'` and `weeklyDays: 99`. `Number(NaN)` range comparisons do not reject NaN; weekly-day validation is absent on this action. `server/model.mjs:84-94`. | Shared strict schemas across setup/settings/API: finite integers, permitted ranges and enums, bounded strings and valid dates. Validate before mutation. |
| B07 | P1 | Onboarding stores 12 answers, but planning mostly uses year, track, minutes and weekly days. Changing beginner versus experienced level produced identical day-80 missions in an isolated comparison. `src/components/overlays.jsx:24-36`; `shared/journey.js:11-19`. | Make starting experience, language, goal, preference, weakness and deadline affect a documented plan policy. Use a diagnostic to establish actual ability. |
| B08 | P0 | Server sessions have token/profile ID only; the cookie has a 30-day Max-Age but the server does not enforce session expiration. `server/index.mjs:23,26,54`. | Add server-enforced idle/absolute expiration, revocation, logout-all-sessions, and invalidation on account suspension or credential changes. |

The first seven findings were reproduced without touching the populated campus database. B08 is confirmed by the session table and identity lookup implementation. These issues explain why passing the present suite is insufficient to trust readiness scores or assignment records.

**3. Student feature backlog**

Responsive rules, a working modal focus trap, scoped staff checks and password hashing already exist. The remaining work is to validate and complete them, rather than claiming those foundations are absent. Accessibility acceptance should use the [W3C WCAG 2.2 reference](https://www.w3.org/WAI/WCAG22/quickref/), including keyboard operation, focus visibility/obscuring, contrast and usable controls.

**6. Helpful additions after the core website works**

These are optional improvements, not reasons to delay a functioning single-college V1:

- Calendar import/export and exam-week scheduling, with one inbox for tasks, interviews and events.
- Topic bookmarks, personal notes, revision flashcards and spaced-repetition review queues.
- Study groups, hackathon team matching, peer project reviews and mentor office-hour bookings.
- Personal proof-of-work portfolio assembled from reviewed projects and real contributions.
- Opt-in year/cohort challenge leagues with useful feedback and clear reward rules.
- Voice interview practice after text interviewing is reliable and feedback is useful.
- Dark mode, reduced motion and selectable journey characters as finishing UI options.
- GitHub/LeetCode sync through authorized integrations, with source and last-sync status.
- Verified certificate wallet and provider recommendations with cost/prerequisite filters.
- Rich debugging environments, employer/recruiter access and multi-college administration after the first institution pilot establishes the workflow.

**7. Recommended completion order and acceptance gates**

| Phase | Deliverable | Required evidence before moving on |
| --- | --- | --- |
| 1. Fix integrity and identity | B01-B08; explicit score semantics; account/session/admin foundations; clean source checkpoint | Checkboxes cannot claim mastery, quiz retakes cannot overwrite unrelated grades, exact tasks match exact resources, invalid API types fail, expired/revoked sessions fail, new users join only an authorized institution |
| 2. Complete the daily learning loop | Diagnostic, genuine curriculum, useful 150-day plan, validated lessons, trusted coding/SQL/lab attempts, catch-up/revision and reminders | A fresh final-year student can follow several representative weeks, lose/recover drafts, miss a day, take leave, replan and complete milestones; all screens agree on the resulting history |
| 3. Complete employability | Persistent AI interviews, evidence-based readiness and job fit, project evidence, full resume, current opportunities and application timeline | A real project and reviewed mock interview improve the correct skills; a job exposes eligibility and gaps; a reviewed resume uses the student's own facts; reminders reach the user |
| 4. Complete college operations | Authoring, assignment attempts/files/rubrics, real challenge engine, placement rounds/eligibility, moderation, durable reports/audit | Teacher publishes to the exact reviewed audience; a student submits the intended attempt; staff review propagates once; a placement round updates the student's timeline; reports reconcile with source records |
| 5. Run and release a pilot | Production configuration, backups/restores, monitoring, pagination, CI, browser/accessibility/load checks, representative user review | Restore a backup; test concurrent student/staff activity and outages; run critical journeys on narrow/wide screens and keyboard; demonstrate versioned deployment/rollback with demo records kept separate |

Year 1-3 curriculum expansion can proceed once the short end-to-end path proves the common learning and scoring model. Each longer path should contain age/year-appropriate foundations, exploration, collaboration, internships and placement preparation; stretching the same few activities across 1,460 days is insufficient.

**8. Definition of a finished first website**

The proposed finish line is a usable, trustworthy single-college web product. It should demonstrate all of the following with fresh accounts, not just a populated demo:

1. A student joins the correct institution, completes setup/diagnostic and receives a credible year/goal/deadline-based plan.
2. Daily work opens the correct activity, survives refresh, validates completion and updates one canonical history.
3. XP/effort, quiz scores, verified mastery, streak and job fit remain distinct and explainable.
4. Practice covers coding, SQL, core-CS/aptitude and practical project debugging with declared verification levels.
5. Missed work, rest, exam weeks and changed deadlines are handled without quietly claiming completion.
6. Courses and projects contain enough genuine material to support the advertised tracks and plans.
7. AI interviews save questions, answers, follow-ups, feedback and improvement actions using the configured provider.
8. Job recommendations have freshness and eligibility, and create specific preparation actions within the time budget.
9. Resumes use reviewed evidence and export cleanly; applications carry the next action and date.
10. Teachers and placement staff can publish, receive, review and report on work with appropriate permissions.
11. Shared social/events support student/staff participation, privacy, reporting and moderation.
12. The website is deployed with account recovery, backups, monitoring, regression coverage and an operational owner.

The immediate highest-value work is Phase 1 followed by a genuinely complete 150-day student path. More seeded records or decorative screens will not resolve the integrity, curriculum and employability gaps identified here.
